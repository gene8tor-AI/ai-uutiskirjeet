# AI:sta arvoa — Työn muutoksesta skaalautuvaan hyötyyn

An editorial series about people, leadership, end-to-end process automation and measurable value. Not another product-news roundup. Generic examples only; public original sources, no employer-internal facts. Repository SPEC-3.8, TASK-ARVOA-001, issues #5/#8.

## Each issue (agent-assisted research; not an autonomous Python scraper)
1. Fetch origin/main, create a unique issue branch and clean isolated worktree from it. Never publish from the old dirty ai-website tree. Check current main for all editions today before work. Normal schedules skip an existing date or date_suffix issue. Only an explicitly requested extra trial may use edition b without overwriting. Do not change RSS or other publications. Read this file, editorial/publish.py and the last issue JSONs.
2. Run `python3 editorial/publish.py --inventory > /tmp/arvoa-archive.json`. Review titles, headings and claims in the entire archive; search body text for candidate concepts, source URLs, synonyms and named studies. Follow up nearest matches by reading their full paragraphs. Compare the last4 issues before selecting the next angle; do not repeat their conclusions with different wording. This semantic review is a human/agent responsibility; string matching is only a guard.
3. Actively web-search in Finnish AND English each run. Find recent original research, measured deployments and contrary/limiting evidence across worker experience, leadership, customer processes, IT/network operations, agent architecture/orchestration and cost. Prefer TTL/OECD/Eurofound, original papers, TM Forum/GSMA and documented deployments; use vendor reports with attribution. Open each used source. Do not use search-result timestamps/snippets as verified publication dates or evidence. Older research is labeled background.
4. Choose3–5 distinct practically useful new developments. Every item must independently pass novelty; do not split one source/story into several items. If fewer than3qualify, SKIP without filler. Fresh evidence must have verified publication date within30days, but reuse of an already covered fresh source is not a new story. If none meets novelty, SKIP; no manufactured issue. Revisit a topic ONLY for a material new result, implementation or conclusion. Explicitly tell readers what changed and reference prior coverage. Never rebrand old research as news.
5. Write a Finnish600–900word digest with3–5news items, not a single-topic essay. Each item has: what is new; effect on people/work/leadership or end-to-end process; business benefit (measured vs claimed vs unknown); evidence limits. End with a short practical synthesis. Do not force every strategic theme into each issue. Claims need source references. Distinguish measured result, expert guidance, vendor claim and illustrative calculation. No unsupported promise of cost savings. Series title and tagline exactly as above.
6. Assemble format=digest-v2 JSON using the revised multi-item example: date, optional edition (one lowercase letter only for authorized extra edition), title, search_queries, items array and synthesis paragraph array. Each item: title, stable topic_id, facts (stable semantic IDs), novelty (archive_reviewed=true,rationale,related_archive; material updates also material_update+previous filenames), sources (id,title,url,published,verified_on,role), source_ids, new, impact, benefit, limits. Record specific archive comparisons per item. Legacy single-topic JSON stays readable history but cannot be newly published. The renderer checks structured history and source overlap but cannot prove semantics; never mark archive_reviewed without actually doing it.
7. Run `python3 editorial/publish.py --input /absolute/candidate.json`, `python3 build_index.py`, `python3 -m unittest discover -s editorial -p 'test_*.py' -v`, `git diff --check`. Review the actual rendered article and diff (citations, math, mobile layout, absence of repeated coverage). Record spec/task acceptance and original-source dates. No email or Notion writes.
8. Make a focused commit and push this issue branch to the existing origin, create a PR and complete a review of the exact changed files. Fix in-scope findings before merging. Do not weaken or bypass repository review policies. For routine later articles reviewer may be a separate exact-diff review pass by the sole owner; when an independent agent is explicitly available/authorized use it. Preserve excluded files, report any blocked push/merge honestly.
9. After reviewed merge, verify the actual Pages build and the public `https://gene8tor-ai.github.io/ai-uutiskirjeet/ai_arvoa_YYYY-MM-DD[_b].html` returns200 with exact merged article bytes. If concurrent feed updates advance main, compare against exact article blob, not a presumed SHA. Only then claim publication. Retry fetches boundedly while reporting progress; no duplicate publishing to fix propagation delay.
10. Report in topic35: verified public URL on first line, title, what is genuinely new, sources, commit/PR, and restrictions. If skipped say why, no invented URL. Do not send extra messages through messaging tools. Leave source branch clean and pushed; preserve issueJSON as the publication/novelty ledger. Future scheduled runs use main, not a fixed stale worktree.

Evidence sections require source IDs; own analysis/recommendations without factual source claims must have `kind: analysis`. At least one fresh evidence URL must be previously unused across the full HTML archive and structured history, even if topic/fact IDs change. Same-URL source revisions alone are insufficient for automated publication; find an independently verifiable new original source or skip. Prior issue links are rendered for explicit material updates. Use the digest-v2 issue as schema example. The first single-topic trial is legacy history only; never recycle its facts. Automated checks do not establish factual or semantic novelty; complete the source and archive review each run.
